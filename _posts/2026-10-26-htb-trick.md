Trick is an Easy Linux machine that features a DNS server and multiple vHost&amp;amp;amp;amp;#039;s that all require various steps to gain a foothold. It requires basic knowledge of DNS in order to get a domain name and then subdomain that can be used to access the first vHost. On the first vHost we are greeted with a Payroll Management System that is vulnerable to SQL Injection. Using sqlmap we find we have file privileges and can read system files. Reading an Nginx configuration file reveals another vHost. This vHost contains a Local File Inclusion (LFI) vulnerability that can be exploited. Sending a mail to one of the users with PHP code embedded and then including that mail with the LFI allows for Remote Code Execution (RCE). After the initial foothold we find a Sudo command that can be executed without a password. The command restarts the fail2ban service. The configuration directory of fail2ban contains a directory that is owned by a group that the current user is part of. The user has write access to the directory and can rename a configuration file and replace it with their own, which leads to Remote Code Execution as root once a ban is triggered.

```
Step 1: Database User Privileges
The first check is performed entirely within the database. The DBMS verifies whether the database user account (the one the web application uses to connect) has the FILE privilege.

Mechanism: If the user lacks this privilege, the database will immediately reject the query with an Access denied error.

Implication: Without the FILE privilege, file reading and writing are impossible. (Note: In environments like MySQL/MariaDB, if this privilege is granted, the query proceeds to the next step).

Step 2: The secure_file_priv Variable (Server Configuration)
If the user has the required privilege, the DBMS next checks its internal security configuration—specifically the secure_file_priv system variable.

Mechanism: This variable dictates where the database is allowed to read or write files. It has three states:

NULL: File operations are completely disabled.
A specific directory path (e.g., /var/lib/mysql-files/): The database is restricted to reading/writing only within this specific directory.
Empty string (''): There are no directory restrictions; the database is allowed to attempt file operations anywhere.
Implication: If this variable is set to NULL or points to a directory different from the target path, the query is blocked here. Notably, at this stage, the DBMS only checks the path string against this variable; it does not yet check if the directory actually exists or if permissions allow writing to it.

Step 3: Operating System Permissions (The Final Hurdle)
Even if the DBMS authorizes the file operation (Steps 1 & 2 pass), it must delegate the actual file creation to the underlying Operating System (e.g., Linux).

Mechanism: The DBMS runs as a specific system process (often under a user like mysql or mariadb). The OS checks if this specific system user has write permissions (e.g., w flag in Linux file permissions) for the target directory.

Implication: Web directories (like /var/www/html/) are typically owned by the web server user (e.g., www-data or nginx) with restrictive permissions (like 755). The database user usually lacks write access to these directories. Consequently, the OS returns a Permission denied error to the DBMS.
```
