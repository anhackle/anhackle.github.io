Pov is a medium Windows machine that starts with a webpage featuring a business site. Enumerating the initial webpage, an attacker is able to find the subdomain dev.pov.htb. Navigating to the newly discovered subdomain, a download option is vulnerable to remote file read, giving an attacker the means to get valuable information from the web.config file. The subdomain uses the ViewState mechanism, which, in combination with the secrets leaked from the web.config file, is vulnerable to insecure deserialization, leading to remote code execution as the user sfitz. Looking at the remote filesystem, an attacker can discover and manipulate a file that reveals the credentials for the user alaading. Once the attacker has code execution as the user alaading the SeDebugPrivilege is abused to gain code execution in the context of a privileged application, ultimately resulting in code execution as nt authority\system.

As you know, *the purpose of ViewState in ASP.NET is to solve the fundamental problem that the web is stateless. When a page is posted back to the server, a completely new instance of the page class is created, and any values the user entered or any control state would normally be lost. ViewState is the default mechanism ASP.NET uses to preserve page and control values across these round trips so the page appears "stateful" to the user. It does this by **serializing** the state into a base64-encoded string that is stored in a hidden form field (usually __VIEWSTATE) and sent to the client, then returned to the server on each postback*

**"It does this by serializing the state"** So we can try to exploit the **insecure deserialization** from that ViewState. But before we can create the payload, we need to find out two import keys: **validationKey** and **decryptionKey**. But what are they ?

*The validationKey is used to generate a Message Authentication Code (MAC) that is attached to the ViewState data. When the page is posted back, ASP.NET recomputes the MAC using this key and compares it to the one in the request. If an attacker modifies even a single byte of the ViewState, the MAC will not match, and the server rejects the request. This is the core defense against ViewState tampering*

*The decryptionKey is used to encrypt the ViewState payload, so that its contents cannot be read by the client. Encryption is not always enabled by default; it is controlled by the application’s viewStateEncryptionMode setting. When encryption is active, the server must use the decryptionKey to decrypt the incoming ViewState before it can even validate or process it*

In the reality, two these keys are usually defined directly by developers in **web.config** file. So we must find a way to read the content of this file on the backend. Fortunately, there is a function on **dev.pov.htb** which allow people to download the cv. So what should we think out right now ? **Local file inclusion**

This file is the result of serializing a **PSCrential Object** by usually running this command:
```
Get-Credential | Export-Clixml -Path ""
```
As you can see in above image, the password has been encrypted and more specifically it was encrypted by **DPAPI** in Windows. DPAPI (Data Protection API) is Windows’ built-in “encrypt this for me” service. Instead of making an application manage its own encryption keys, DPAPI derives protection from the logged-on user’s Windows credentials (or the local machine) and returns an encrypted blob. Applications still have to store that blob themselves—DPAPI only encrypts/decrypts it.

To manually decrypt the password, we can use this command to deserialize the PSCrential Object again:
```
PS C:\users\sfitz\Documents> ls

PS C:\users\sfitz\Documents> $credential.GetNetworkCredential().username

PS C:\users\sfitz\Documents> $credential.GetNetworkCredential().password
```

## P3 & P4
I have tried many scripts (for example [this](https://www.powershellgallery.com/packages/PoshPrivilege/0.3.0.0/Content/Scripts%5CEnable-Privilege.ps1) and [this](https://www.leeholmes.com/adjusting-token-privileges-in-powershell/)) but still not be able to turn it on.<br>
After some researching, I find out some interesting points related to access token in windows like this:
- Layer 1 (Network Logon Filtering) prevents simple lateral movement attacks via WinRM/PSRemoting
    
- Layer 2 (UAC Token Filtering) prevents ordinary local privilege escalation attempts

Because our present logon now is through a reverse shell, it is a network logon.
